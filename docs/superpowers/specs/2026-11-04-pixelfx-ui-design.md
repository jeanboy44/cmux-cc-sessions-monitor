# pixelfx 마법 UI 재설계

## 의도

세션 카드를 pixelfx(https://github.com/patch-gg/pixelfx, MIT)의 히어로·더미·마법 연출로 완전히 교체한다. 사용자는 목록을 훑다가 "어느 세션이 일하는 중인지, 입력을 기다리는지"를 움직임만으로 알아챈다. 기존 Pochi 마스코트와 A/B 타일 디자인은 제거한다. 세션 정보(상태, 브랜치, PR, 미리보기, 창 그룹, 선택·포커스 동작)는 유지한다.

## 목표

- 카드마다 pixelfx 히어로(24×38)가 왼쪽, 더미(24×38)가 오른쪽에 서 있고, 히어로가 마법을 쓰면 더미가 맞는다. 캐릭터 스프라이트와 팔레트는 원본 그대로 쓴다.
- 테마 5종: fire, water, ice, lightning, melee. 설정에서 기본 테마를 고르고, 선택한 카드에서 `t`로 그 카드만 순환한다. 카드별 테마는 프로젝트 폴더(cwd)를 키로 config에 저장한다(세션 id는 재시작마다 바뀌므로). (제 판단)
- Running 상태에서는 테마의 마법 연출을 랜덤 변형(시드·연출 종류)과 랜덤 간격으로 계속 보여 준다.
- 포팅은 방식 B: 코어 엔진과 테마당 2~3개 연출을 Rust로 옮긴다. 원본 Node 렌더와 같은 시드의 프레임을 비교하는 골든 테스트로 정확도를 검증한다. 비교는 비트 단위 일치가 아니라 픽셀 허용 오차(차이 픽셀 비율)로 한다: JS와 Rust의 삼각함수 구현이 달라 입자 시뮬레이션에서 오차가 누적되기 때문이다(제 판단).
- NOTICE에 patch-gg/pixelfx, Hugo Duprez(Sprite Fusion), Hollow Crown(rehan-remade)의 MIT 고지를 넣는다.
- `h`/`l` 행 넘김은 이미 구현됨(커밋 전): 행 끝에서 `l`은 다음 행 첫 카드, 행 처음에서 `h`는 이전 행 마지막 카드, 창 그룹도 넘는다.

## 비목표 / 반(反)목표

- pixelfx 57종 전체를 옮기지 않는다. 5개 테마 밖의 카테고리(arcane 일부는 의존 연출로만)는 포팅하지 않는다.
- 브라우저/JS 런타임이나 Node 의존을 최종 바이너리에 넣지 않는다. 골든 프레임 생성에만 개발 PC에서 Node를 쓴다.
- 실제로 일하는 세션이 한눈에 안 보일 만큼 장면이 화려해지면 실패다. 상태 구분은 항상 읽혀야 한다.
- 터미널에서 CPU를 과하게 쓰면 실패다. 렌더는 보이는 카드만, 목표 fps 이하로 제한한다.

## 카드 구성

위쪽은 장면 영역, 아래쪽은 정보 줄(세션 이름, 상태, 브랜치, PR)이다. **1단계는 원본 픽셀 크기 그대로(1:1) 그린다**(사용자 결정: 먼저 원본 크기로 만들어 보고, 이후 크기를 조정). 렌더러는 점자(2×4 도트, 칸당 색 1개)이며 이것은 제 판단이다. 히어로·더미는 각 24×38px = 12칸×10줄, 간격을 줄인 장면(약 90px)은 약 45칸×10줄이므로 카드는 장면 + 정보 줄 약 12줄, 한 줄에 2장 정도다. 이전 설계서의 "40칸×14줄, 반블록" 수치는 폐기한다.

크기 조정은 2단계로 미룬다: 렌더 배율(1:1, 2×2 합치기 등)을 한 곳의 설정값으로 두어 나중에 바꿀 수 있게 하고, 필요하면 Kitty 그래픽 프로토콜(실제 이미지) 가능성을 cmux에서 확인한다. 터미널이 한 장면도 못 담을 만큼 작거나 미리보기(`p`) 모드일 때는 장면 없는 한 줄짜리 간단 카드로 바꾼다(제 판단). 선택된 카드는 기존처럼 cmux 파랑 테두리, 창 그룹 구분선과 `h`/`l`/`j`/`k` 이동은 유지한다.

## 상태별 장면 (제 판단)

- Running: 테마의 마법 연출을 랜덤하게 반복 시전.
- NeedsInput: 마법을 모은(spell-charge) 자세로 대기하며 깜빡이고, 정보 줄에도 입력 대기를 눈에 띄게 표시.
- Idle: 대기 자세(READY), 더미는 가만히 서 있음.
- Done: 더미가 그을린 스킨, 히어로 승리 포즈. 정적.
- Unknown: 어둡게 정적.

## 포팅 범위

원본 소스는 `src/core`(math, color, particles, sim, painter, fx, actor, rig, poses, act, chain, shapes ≈127KB)와 `src/fx/<category>`(연출당 5~12KB + 카테고리 `_lib.js`)로 구성된다. 연출은 `draw(painter, t, options)` 형태의 시간 함수이고, 프레임은 `color`/`light` 두 개의 `Uint32Array`(불투명 픽셀 + 가산 발광)를 `composite()`로 합친다. `moves/*`는 히어로 자세 트랙(`act`)과 `chain([...])`으로 연출을 시간순으로 이어 붙인 완성 시퀀스다.

- fire: `moves/fireball-throw`(+ `arcane/spell-charge`, `fire/fireball`, `explosions/small-explosion`) 외 1~2개.
- ice: `moves/ice-lance-throw`(+ 의존 연출) 외 1~2개.
- lightning: `moves/lightning-call`(+ 의존 연출) 외 1~2개.
- melee: `moves/sword-combo`, `moves/dash-strike`(+ 의존 연출).
- water: 완성 move가 없어 직접 조합(제 판단): `spell-charge` → `water/water-orb` 또는 `water/water-jet`이 더미까지 날아감 → `water/splash` 또는 `water/wave-crash`. 구조는 `fireball-throw`의 `chain`과 같다.

정확한 연출 목록은 구현 계획에서 의존 관계를 따라 확정한다. 시드 난수·노이즈(`math.js`)는 정수 연산 부분을 원본과 같게 맞추고, 부동소수 함수는 허용 오차 안에서 같으면 된다.

## 렌더링

Rust에서 프레임(`color`/`light`)을 만들고 `composite()`로 RGBA 픽셀 버퍼를 얻은 뒤, 카드 영역 크기에 맞게 잘라 점자로 ratatui 버퍼에 쓴다(칸의 색은 켜진 점들의 평균/우세색). 알파/발광은 장면 전용 어두운 배경색(직접 칠함, 터미널 배경은 읽지 않음)과 합성한다. 애니메이션은 약 15fps로 실시간 계산하고 장면이 보일 때만 틱을 빠르게 한다. 카드별 시드는 cwd와 시전 횟수로 정하고, 카드마다 시작 시점을 어긋나게 하며, 상태가 바뀌면 현재 시전을 마치고 전환한다(모두 제 판단). 애니메이션 시간 `t`는 기존 UI 틱(앱 루프)에서 받는다. 24비트 색을 못 쓰는 터미널은 지원하지 않는다(cmux는 지원).

## 제약

- macOS 전용, 기존 Rust 2021 / ratatui 0.30 / crossterm 0.29, 새 의존성은 최소화(이미지·JS 런타임 금지).
- 개인정보 가드 테스트(`tests/no_personal_info.rs`)를 통과해야 한다: 문서·픽스처에 홈 디렉터리 절대경로, 실제 UUID/회사명 금지.
- 골든 프레임 픽스처는 저장소에 커밋하되 크기를 작게 유지한다(대표 몇 프레임만).

## 빌더에게 맡기는 것

- 모듈 분리(`src/fx/…`)와 포팅 순서, 골든 테스트 형식, 장면 자르기·축소 세부, 연출 종류·시전 간격의 정확한 값, 설정 화면 UI 세부(기본 테마 선택, `t` 키 동작).
- 단계 제안: ① 엔진+히어로·더미 정적 렌더를 카드에 표시 ② `act`+fire 테마 한 개 연출 ③ 나머지 테마 ④ 상태 매핑·설정·정리.
